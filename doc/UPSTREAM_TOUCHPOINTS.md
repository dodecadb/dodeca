# Upstream touchpoints

Dodeca runs on an unmodified Neo4j Community: its single jar goes into Neo4j's
`lib/`. It builds on the Neo4j classes listed here. After every Neo4j upgrade,
diff each of them between the old and the new Neo4j version and carry relevant
changes over.

## Neo4j classes Dodeca builds on

| Neo4j class | Dodeca code | How |
|---|---|---|
| `NeoBootstrapper` | `DodecaBootstrapper` | Subclass. Starts `DodecaEditionModule`, or `ClusterEditionModule` with clustering enabled, and reports the Enterprise edition. |
| `CommunityEditionModule` | `DodecaEditionModule` | Subclass. `createDatabaseContextProvider` is a copy of Community's that uses `DatabaseManager` instead of `DatabaseLifecycles`, which allows only two databases, and `DodecaDatabaseContextFactory` instead of `DefaultDatabaseContextFactory`. `registerDefaultDatabaseInitializer` is overridden because Community keeps its default database starter in a private field. `createDefaultDatabaseResolver` and `createSecurityModule` are copies of Community's that use `DodecaDefaultDatabaseResolver` and `DodecaSecurityModule`. `createDatabaseContextProvider` registers what Community's registers there, such as the model-based database id and reference repositories, and in place of the `CommunityDefaultQueryLanguageLookup` that the query router resolves Dodeca's `DefaultLanguages`: compare it with Community's after an upgrade, as a missing dependency fails every start. |
| `GraphDatabaseSettings.udc_enabled`, `BoltConnector.enable_discovery` | `DodecaEditionModule` | Neo4j sends anonymous usage data and, since 2026, announces each server on the local network for its fleet tools, both with the edition, which Dodeca reports as Enterprise: the edition module sets both settings to false unless the operator set them (`UsageDataTest`, `FleetDiscoveryTest`). Fleet Manager (`dbms.fleet_manager.enabled`, `fleetManagement.*`) sends nothing until an operator registers a token. |
| `CommunityEditionModule` | `ClusterEditionModule` | Through `DodecaEditionModule`. `registerDatabaseInitializers` is overridden so that only the member founding the cluster initializes the system graph, with `getSystemGraphComponents()`. |
| `CommunityEditionModule`, `AbstractEditionModule.createGlobalReadOnlyChecker`, `DefaultReadOnlyDatabases`, `ReadOnlyChangeListener`, `SystemGraphReadOnlyListener`, `SystemGraphReadOnlyDatabaseLookupFactory` | `ClusterEditionModule`, `LeaderBalancer` | `createGlobalReadOnlyChecker` is a copy of Community's with a `ReadOnlyChangeListener`, which Community leaves a no-op: each refresh of the read-only databases (a change of `server.databases.read_only` and the like, or a commit to `system`) asks the balancer to look, so that a leader hands over a database that turned read-only on it. `isReadOnlyLocally` tells the databases read-only on this member by its configuration, which members report to each other. |
| `DatabaseEventListener.databaseShutdown`, `Database.stop` | `ReplicationService`, `ReplicatedDatabase.stop` | Neo4j calls `databaseShutdown` before it waits for the database's transactions to close. A leader stops granting leases there and lets the commits under way finish before its Raft group stops applying, or their clients would not learn whether they committed. |
| `DatabaseLifecycles` | `DatabaseManager` | Port, for many databases. |
| `AbstractDatabase.start`, `handleStartupFailure`, `Database` | `DatabaseManager.renew` | Neo4j 2026 shuts a database whose start failed down, but the `Database` object keeps parts of that start: started again, it starts its transaction logs twice, or finds two `KernelVersionProvider`s and fails. `DatabaseManager` registers a new context, from `DodecaDatabaseContextFactory`, in place of one whose start failed (`StandaloneDatabasesTest`). Recheck after an upgrade whether Neo4j starts a failed `Database` afresh. |
| `ModularDatabaseCreationContext.getWatcherServiceFactory`, `DatabaseLayoutWatcher`, `DefaultFileDeletionListenerFactory`, `FileWatcher` | `DodecaDatabaseContextFactory`, `RetryingFileWatcher` | Each database's `DatabaseLayoutWatcher` is built as Neo4j builds it, but on a `FileWatcher` that watches a directory again, at most 3 times, when `watch` fails with a `NoSuchFileException` while the directory exists: the JDK's polling watch service (macOS, AIX) reads every entry of a directory it registers, and fails if one goes meanwhile, as when another database's copy moves into place. Neo4j 2026 cannot start a database again once its start failed so: the shutdown checkpoint of its cleanup finds the checkpoint log not started, and the next start finds the dependencies of the first. |
| `DefaultDatabaseContextFactory` | `DodecaDatabaseContextFactory` | Port. Differs in the constraint semantics, the Cypher engine, and for replicated databases in the hosting mode (`HostedOnMode.RAFT` for a primary, `REPLICA` for a secondary, which Neo4j treats alike), leases, commit process and ID allocation, which a database takes from its current hosting each time it starts: `system` switches between primary and secondary while stopped (`SwitchingHostedDatabase`), keeping the `Database` that Neo4j and its components hold. | `TransactionalProcessFactory`, `InternalTransactionCommitProcess`, `TransactionCommitmentFactory`, `IdStoreTransactionIdGenerator`, `CompleteBatchRepresentation`, `TransactionApplicationMode.EXTERNAL`, `TransactionIdStore` | `SecondaryDatabase` | A secondary refuses transactions of its own and applies those it pulls through a local commit process of its own, as a follower applies Raft entries: in external mode, so that ID generators track the IDs they use, with each transaction's consensus index, one chain per pull, which Neo4j's appender forces once. After each transaction it compares the checksum Neo4j computed with the upstream's. |
| `DatabaseEventListenerAdapter` (`databaseStart`, `databaseShutdown`) | `Secondaries` | A secondary pulls from when Neo4j started the database until it shuts down; a pause ends when it starts again. |
| `CommunityCypherEngineProvider` | `DodecaCypherEngineProvider` | Subclass; overrides `makeCompilerFactory`. |

## Code ported from DozerDB

Dodeca began as an add-on to [DozerDB](https://dozerdb.org) and kept its source
as a git subtree. On 2026-10-19 the DozerDB code it built on was ported to
Kotlin and DozerDB was removed; that code is now in `dodeca-core` and
`dodeca-plugin`. The port started from
[dozerdb/dozerdb-core](https://github.com/dozerdb/dozerdb-core) branch
`neo4j-5.26.8`, commit `f76393e`, and later moved to Neo4j 2026. Ported files keep the Neo4j and DozerDB
copyright notices and add a Dodeca modification notice; [`COMPATIBILITY.md`,
"From DozerDB"](COMPATIBILITY.md#from-dozerdb), lists how Dodeca behaves
differently.

## Apache Ratis code Dodeca builds on

`consensus-ratis` runs on Apache Ratis 3.3.1 and changes three of its classes.
After every Ratis upgrade, diff the classes listed here between the old and the
new Ratis version and carry relevant changes over; `PatchedRatisClassesTest`
fails until the copies below are redone, or dropped once Ratis has their fixes.

| Ratis class | Dodeca code | How |
|---|---|---|
| `GrpcLogAppender`, `GrpcFactory` | `PatchedGrpcLogAppender`, `PatchedGrpcFactory`, `PatchedGrpcRpcType` | A copy of `GrpcLogAppender`, in its Ratis package for the package-private `GrpcServerProtocolClient`, and formatted as upstream so that it diffs against it; each change starts with a `Dodeca` comment. After a failed request, Ratis gives up on the leader's two streams to the follower without ending them, and one stayed open for each failed request; Dodeca's leader ends them, and their late failures no longer reset the streams in use. `PatchedGrpcFactory` is Ratis' `GrpcFactory` with this appender and the services below; it is in Ratis' package for the package-private helpers that build the services' TLS contexts. `PatchedGrpcRpcType`, set as `raft.rpc.type`, creates it. |
| `GrpcServicesImpl`, `GrpcServerProtocolClient` | `PatchedGrpcServicesImpl`, `PatchedGrpcServerProtocolClient`, `RatisConsensusLog.start` | Copies, made and marked as `PatchedGrpcLogAppender`; the services copy only creates the client copy. Ratis' connections to other members have no keep-alive and no connect timeout, and Ratis gives no hook to add them. A connection to a member whose packets were dropped, as when the network between them failed, stayed open while TCP resent what the member did not acknowledge, waiting twice as long before each resend: once the network healed, the leader reached the member only with the next resend, as long after as the outage had lasted, up to two minutes. Dodeca's connections ping the member after 10 seconds without hearing from it, also without calls under way, and close when a ping or data goes unacknowledged for 10 seconds (gRPC sets this as `TCP_USER_TIMEOUT` on Linux); connecting gives up after 3 seconds, so that attempts to reach a member that cannot be reached start every few seconds. The members' servers permit these pings and ping connections that sent nothing for as long themselves, so that the end of a connection another member gave up on during an outage closes. `CutOffMemberIT` cuts a member off for half a minute; it caught up 23 seconds after the network healed, and within about a second since. |
| `GrpcServerProtocolService`, `RaftServerProtocolServiceGrpc`, `RaftRpcRequestProto.replyId`, `GrpcUtil.wrapException` | `RefuseUnavailableGroups`, `RefuseOtherMembers`, `RefuseWhileStopping` | gRPC interceptors in front of Ratis' services. `RefuseUnavailableGroups` answers the appends and snapshot notifications for a group closed on this member, as after an entry failed to apply, or still starting, before Ratis sees them, with the failure and call id Ratis answers for a group that is not ready: Ratis would log an error for each. `RefuseOtherMembers` answers the requests of other members addressed to another member id than this one's (`replyId`) the same way: Ratis does not check it, and would answer for a member that this one replaced at its address, while the groups still count that member. `RefuseWhileStopping` takes no requests once the member stops, as Ratis closes its groups before its server. |
| `RoleInfoProto`, `FollowerInfoProto`, gRPC's `ServerTransportFilter` and `ServerInterceptor` | `MemberConnections`, `RatisConsensusLog.connections` | `dbms.cluster.protocols`: Ratis gives no hook on its client channels, so a leader's outbound Raft connections come from its role information, the followers that answered within twice the longest election timeout; inbound connections from a transport filter and an interceptor on the consensus port. gRPC calls `transportTerminated` with null attributes for a connection that ended before it was ready, as after a failed TLS handshake; a filter that throws there keeps the server from terminating. |
| `RaftServer.Division.getRaftLog` | `RatisConsensusLog` | A group's division can be running before its log is initialised, while `getRaftLog` throws `IllegalStateException`; Dodeca reports the group as starting meanwhile. |
| `GrpcTlsConfig` (built with a `KeyManager` and a `TrustManager`) | `ReloadableTls`, `TlsContexts` | Raft channels take their TLS from key and trust managers that use the current certificate and trusted authorities, so that a TLS reload reaches connections made afterwards. gRPC clients always ask the trust manager to check that the server's certificate names the address dialled, which it does only when `verify_hostname` was set at start. Protocols, cipher suites and client authentication shape a channel when it is made, so they keep their values until a restart. |

A known Ratis 3.3.1 bug that Dodeca does not work around:
`RaftServerProxy.groupAddAsync` drops a division whose `start()` failed without
closing it, so the lock on the group's storage directory stays held until the
JVM exits. A database whose Raft group failed to start, as when its storage
could not be read, starts again only after the member restarts. Upstream fix:
close the division when the add fails. Check whether a Ratis upgrade fixes it.

## Neo4j behaviour that single fsync relies on

`SingleFsyncFileSystem` wraps Neo4j's file system instead of changing Neo4j
code. It depends on the following, verified against Neo4j 2026.10.2. Recheck
them after every Neo4j upgrade; the unit and power-loss tests in
`dodeca-cluster` catch most such changes.

- Transaction log and checkpoint files are opened for writing through the DBMS
  `FileSystemAbstraction` (`org.neo4j.wal.files.TransactionLogChannelAllocator`),
  which an external dependency may replace (`GlobalModule`), and are forced
  only through `StoreChannel.flush()` (`TransactionLogFile`,
  `DetachedCheckpointAppender`).
- They are named `neostore.transaction.db.<n>` and `checkpoint.<n>` in
  `<transactions root>/<database>/` (`TransactionLogFilesHelper`).
- The page cache writes store pages through `StoreChannel` write methods of
  channels from the same file system, while it holds the page's flush lock
  (`SingleFilePageSwapper`, `MuninnPageCache`). Its asynchronous writes, which
  go to the file descriptor directly, need `server.memory.pagecache.async` and
  an `AsyncIOProvider`; Neo4j Community has only `AbsentAsyncIOProvider`, whose
  accessor writes nothing asynchronously.
- The checkpointer fixes the checkpointed position before it flushes the store,
  and writes the checkpoint record after (`org.neo4j.wal.checkpoint.CheckPointerImpl`).
- Recovery reads `internal.dbms.tx_log.fail_on_corrupted_log_files` from the
  configuration it is given, which holds the DBMS setting: it overrides only
  its own settings, in a `DatabaseConfig` over that configuration
  (`Recovery.recoveryOptimizedConfig`).
- `DetachedCheckpointAppender.shutdown` closes its channel twice; the wrapper's
  `close` is idempotent.
