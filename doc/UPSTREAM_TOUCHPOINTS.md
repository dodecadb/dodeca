# Upstream touchpoints

DozenDB runs on an unmodified Neo4j Community: its single jar goes into Neo4j's
`lib/`. It builds on the Neo4j classes listed here. After every Neo4j upgrade,
diff each of them between the old and the new Neo4j version and carry relevant
changes over.

## Neo4j classes DozenDB builds on

| Neo4j class | DozenDB code | How |
|---|---|---|
| `NeoBootstrapper` | `DozenDbBootstrapper` | Subclass. Starts `DozenDbEditionModule`, or `ClusterEditionModule` with clustering enabled, and reports the Enterprise edition. |
| `CommunityEditionModule` | `DozenDbEditionModule` | Subclass. `createDatabaseContextProvider` is a copy of Community's that uses `DatabaseManager` instead of `DatabaseLifecycles`, which allows only two databases, and `DozenDbDatabaseContextFactory` instead of `DefaultDatabaseContextFactory`. `registerDefaultDatabaseInitializer` is overridden because Community keeps its default database starter in a private field. `createDefaultDatabaseResolver` and `createSecurityModule` are copies of Community's that use `DozenDbDefaultDatabaseResolver` and `DozenDbSecurityModule`. `createDatabaseContextProvider` registers what Community's registers there, such as the model-based database id and reference repositories and the `CommunityDefaultQueryLanguageLookup` that the query router resolves: compare it with Community's after an upgrade, as a missing dependency fails every start. |
| `GraphDatabaseSettings.udc_enabled`, `BoltConnector.enable_discovery` | `DozenDbEditionModule` | Neo4j sends anonymous usage data and, since 2026, announces each server on the local network for its fleet tools, both with the edition, which DozenDB reports as Enterprise: the edition module sets both settings to false unless the operator set them (`UsageDataTest`, `FleetDiscoveryTest`). Fleet Manager (`dbms.fleet_manager.enabled`, `fleetManagement.*`) sends nothing until an operator registers a token. |
| `CommunityEditionModule` | `ClusterEditionModule` | Through `DozenDbEditionModule`. `registerDatabaseInitializers` is overridden so that only the member founding the cluster initializes the system graph, with `getSystemGraphComponents()`. |
| `CommunityEditionModule`, `AbstractEditionModule.createGlobalReadOnlyChecker`, `DefaultReadOnlyDatabases`, `ReadOnlyChangeListener`, `SystemGraphReadOnlyListener`, `SystemGraphReadOnlyDatabaseLookupFactory` | `ClusterEditionModule`, `LeaderBalancer` | `createGlobalReadOnlyChecker` is a copy of Community's with a `ReadOnlyChangeListener`, which Community leaves a no-op: each refresh of the read-only databases (a change of `server.databases.read_only` and the like, or a commit to `system`) asks the balancer to look, so that a leader hands over a database that turned read-only on it. `isReadOnlyLocally` tells the databases read-only on this member by its configuration, which members report to each other. |
| `DatabaseEventListener.databaseShutdown`, `Database.stop` | `ReplicationService`, `ReplicatedDatabase.stop` | Neo4j calls `databaseShutdown` before it waits for the database's transactions to close. A leader stops granting leases there and lets the commits under way finish before its Raft group stops applying, or their clients would not learn whether they committed. |
| `DatabaseLifecycles` | `DatabaseManager` | Port, for many databases. |
| `AbstractDatabase.start`, `handleStartupFailure`, `Database` | `DatabaseManager.renew` | Neo4j 2026 shuts a database whose start failed down, but the `Database` object keeps parts of that start: started again, it starts its transaction logs twice, or finds two `KernelVersionProvider`s and fails. `DatabaseManager` registers a new context, from `DozenDbDatabaseContextFactory`, in place of one whose start failed (`StandaloneDatabasesTest`). Recheck after an upgrade whether Neo4j starts a failed `Database` afresh. |
| `ModularDatabaseCreationContext.getWatcherServiceFactory`, `DatabaseLayoutWatcher`, `DefaultFileDeletionListenerFactory`, `FileWatcher` | `DozenDbDatabaseContextFactory`, `RetryingFileWatcher` | Each database's `DatabaseLayoutWatcher` is built as Neo4j builds it, but on a `FileWatcher` that watches a directory again, at most 3 times, when `watch` fails with a `NoSuchFileException` while the directory exists: the JDK's polling watch service (macOS, AIX) reads every entry of a directory it registers, and fails if one goes meanwhile, as when another database's copy moves into place. Neo4j 2026 cannot start a database again once its start failed so: the shutdown checkpoint of its cleanup finds the checkpoint log not started, and the next start finds the dependencies of the first. |
| `DefaultDatabaseContextFactory` | `DozenDbDatabaseContextFactory` | Port. Differs in the constraint semantics, the Cypher engine, and for replicated databases in the hosting mode (`HostedOnMode.RAFT` for a primary, `REPLICA` for a secondary, which Neo4j treats alike), leases, commit process and ID allocation, which a database takes from its current hosting each time it starts: `system` switches between primary and secondary while stopped (`SwitchingHostedDatabase`), keeping the `Database` that Neo4j and its components hold. After each transaction it compares the checksum Neo4j computed with the upstream's. |
| `DatabaseEventListenerAdapter` (`databaseStart`, `databaseShutdown`) | `Secondaries` | A secondary pulls from when Neo4j started the database until it shuts down; a pause ends when it starts again. |

A known Ratis 3.3.1 bug that DozenDB does not work around:
`RaftServerProxy.groupAddAsync` drops a division whose `start()` failed without
closing it, so the lock on the group's storage directory stays held until the
JVM exits. A database whose Raft group failed to start, as when its storage
could not be read, starts again only after the member restarts. Upstream fix:
close the division when the add fails. Check whether a Ratis upgrade fixes it.

## Neo4j behaviour that single fsync relies on

`SingleFsyncFileSystem` wraps Neo4j's file system instead of changing Neo4j
code. It depends on the following, verified against Neo4j 2026.10.2. Recheck
them after every Neo4j upgrade; the unit and power-loss tests in
`dozendb-cluster` catch most such changes.

- Transaction log and checkpoint files are opened for writing through the DBMS
  `FileSystemAbstraction` (`org.neo4j.wal.files.TransactionLogChannelAllocator`),
  which an external dependency may replace (`GlobalModule`), and are forced
  only through `StoreChannel.flush()` (`TransactionLogFile`,
  `DetachedCheckpointAppender`).
- They are named `neostore.transaction.db.<n>` and `checkpoint.<n>` in
  `<transactions root>/<database>/` (`TransactionLogFilesHelper`).
- The page cache writes store pages through `StoreChannel` write methods of
  channels from the same file system, while it holds the page's flush lock
  (`SingleFilePageSwapper`, `MuninnPageCache`). Its asynchronous writes, which
  go to the file descriptor directly, need `server.memory.pagecache.async` and
  an `AsyncIOProvider`; Neo4j Community has only `AbsentAsyncIOProvider`, whose
  accessor writes nothing asynchronously.
- The checkpointer fixes the checkpointed position before it flushes the store,
  and writes the checkpoint record after (`org.neo4j.wal.checkpoint.CheckPointerImpl`).
- Recovery reads `internal.dbms.tx_log.fail_on_corrupted_log_files` from the
  configuration it is given, which holds the DBMS setting: it overrides only
  its own settings, in a `DatabaseConfig` over that configuration
  (`Recovery.recoveryOptimizedConfig`).
- `DetachedCheckpointAppender.shutdown` closes its channel twice; the wrapper's
  `close` is idempotent.
