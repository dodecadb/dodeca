# Upstream touchpoints

DozenDB runs on an unmodified Neo4j Community: its single jar goes into Neo4j's
`lib/`. It builds on the Neo4j classes listed here. After every Neo4j upgrade,
diff each of them between the old and the new Neo4j version and carry relevant
changes over.

## Code ported from DozerDB

DozenDB began as an add-on to [DozerDB](https://dozerdb.org) and kept its
source as a git subtree. On 2026-10-19 the DozerDB code it built on was ported
to Kotlin and DozerDB was removed; that code is now in `dozendb-core` and
`dozendb-plugin`. The port started from
[dozerdb/dozerdb-core](https://github.com/dozerdb/dozerdb-core) branch
`neo4j-5.26.8`, commit `f76393e`. Ported files keep the Neo4j and DozerDB
copyright notices and add a DozenDB modification notice; `COMPATIBILITY.md`

## Apache Ratis code DozenDB builds on

`consensus-ratis` runs on Apache Ratis 3.3.1 and changes one of its classes.
After every Ratis upgrade, diff the classes listed here between the old and the
new Ratis version and carry relevant changes over; `PatchedGrpcLogAppenderTest`
fails until the copy below is redone, or dropped once Ratis has its fix.

| Ratis class | DozenDB code | How |
|---|---|---|
| `GrpcLogAppender`, `GrpcFactory` | `PatchedGrpcLogAppender`, `PatchedGrpcRpcType` | A copy of `GrpcLogAppender`, in its Ratis package for the package-private `GrpcServerProtocolClient`, and formatted as upstream so that it diffs against it; each change starts with a `DozenDB` comment. After a failed request, Ratis gives up on the leader's two streams to the follower without ending them, and one stayed open for each failed request; DozenDB's leader ends them, and their late failures no longer reset the streams in use. `PatchedGrpcRpcType`, set as `raft.rpc.type`, is Ratis' `GrpcFactory` with this appender. |
| `GrpcServerProtocolService`, `RaftServerProtocolServiceGrpc`, `GrpcUtil.wrapException` | `RefuseUnavailableGroups`, `RefuseWhileStopping` | gRPC interceptors in front of Ratis' services. `RefuseUnavailableGroups` answers the appends and snapshot notifications for a group closed on this member, as after an entry failed to apply, or still starting, before Ratis sees them, with the failure and call id Ratis answers for a group that is not ready: Ratis would log an error for each. `RefuseWhileStopping` takes no requests once the member stops, as Ratis closes its groups before its server. |
| `RaftServer.Division.getRaftLog` | `RatisConsensusLog` | A group's division can be running before its log is initialised, while `getRaftLog` throws `IllegalStateException`; DozenDB reports the group as starting meanwhile. |

A known Ratis 3.3.1 bug that DozenDB does not work around:
`RaftServerProxy.groupAddAsync` drops a division whose `start()` failed without
closing it, so the lock on the group's storage directory stays held until the
JVM exits. A database whose Raft group failed to start, as when its storage
could not be read, starts again only after the member restarts. Upstream fix:
close the division when the add fails. Check whether a Ratis upgrade fixes it.

## Neo4j behaviour that single fsync relies on

`SingleFsyncFileSystem` wraps Neo4j's file system instead of changing Neo4j
code. It depends on the following, verified against Neo4j 5.26. Recheck them
after every Neo4j upgrade; the unit and power-loss tests in `dozendb-cluster`
catch most such changes.

- Transaction log and checkpoint files are opened for writing through the DBMS
  `FileSystemAbstraction` (`TransactionLogChannelAllocator`), which an external
  dependency may replace (`GlobalModule`), and are forced only through
  `StoreChannel.flush()` (`TransactionLogFile`, `DetachedCheckpointAppender`).
- They are named `neostore.transaction.db.<n>` and `checkpoint.<n>` in
  `<transactions root>/<database>/` (`TransactionLogFilesHelper`).
- The page cache writes store pages through `StoreChannel` write methods of
  channels from the same file system, while it holds the page's flush lock
  (`SingleFilePageSwapper`, `MuninnPageCache`).
- The checkpointer fixes the checkpointed position before it flushes the store,
  and writes the checkpoint record after (`CheckPointerImpl`).
- Recovery reads `internal.dbms.tx_log.fail_on_corrupted_log_files` from the
  DBMS configuration: `Config.Builder.fromConfig` drops per-database settings
  (`Recovery.recoveryOptimizedConfig`).
- `DetachedCheckpointAppender.shutdown` closes its channel twice; the wrapper's
  `close` is idempotent.
